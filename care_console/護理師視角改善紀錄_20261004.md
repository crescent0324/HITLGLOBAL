# 護理師操作情境檢視與系統改善

日期：2026 年 10 月 4 日（臺灣時間）。

本輪由同一開發者先以護理師操作情境檢視，再實作改善。下列問題是角色扮演的設計檢視，未訪談實際護理師，也未以此宣稱使用性、工作負荷或照護成效改善。環境全部使用虛構住民及本機訊息。

## 問題與實際修正

| 操作情境中的問題 | 修正內容 | 驗證與界線 |
|---|---|---|
| 一進網頁，要先處理誰？逐床查看容易漏掉訊息。 | 首頁新增訊息待辦，依案件訊息風險、是否接手及建立時間排序；列出近期詢問、等待時間、接手者與下一步，提供「尚未接手／由我處理／交班給我」篩選。 | 程式測試確認排序及住民範圍；網頁實際列出 R001 人工案件。排序依系統訊息分級，並非臨床急迫程度判定。 |
| 為什麼系統要轉人工？之前回答過什麼？ | 顯示轉人工原因、最近三則使用者訊息、相關分級紀錄及先前的固定服務摘要。 | 分級紀錄顯示最近一筆符合案件風險層級的保存事件；不宣稱一定是最初觸發案件的事件，也不使用 AI 補寫理由。 |
| 卡片的警示是住民狀況，還是家屬訊息？ | 明確區分「照護回報」與「訊息處理狀態」，另列照護回報需確認清單。需追蹤／需優先確認的新回報必須填寫原因。 | 不以生命徵象數值推論健康狀況，也不把照護回報自動建立為訊息案件。此輪未建立院內照護任務結案系統。 |
| 換班後，誰負責？下一班要從哪裡開始？ | 目前接手者填寫已處理內容、下一步與待確認事項，指定接班帳號；對方能先閱讀內容，確認接收後才轉移接手權限。保留交班及操作紀錄。 | 實際以 nurse → nurse2 走完；接收前仍由 nurse 負責，接收後 nurse2 可以回覆，案件持續人工處理。 |
| 交班提出後又有新訊息，下一班會沿用過時內容嗎？ | 新訊息或回覆使交班快照過時，接收被拒絕；原接手者須更新進度並重新提出。更新進度會取消舊交班。 | 程式測試確認拒絕過時交班、取消舊提案及重新提出後可接收；未新增自動摘要來替代人員確認。 |
| 開另一個視窗或重新整理，會不會蓋掉正在寫的進度？ | 同案件更新紀錄時保留未保存表單；保存採版本比對，舊版本不能覆蓋新紀錄，另提供重新載入保存內容。 | 網頁確認更新紀錄後未保存文字仍在；程式測試確認版本衝突回傳 409。關閉視窗或離開頁面前，仍須先保存。 |
| 能否少做一次輸入，直接接院內資料？ | 維持既有 CSV 匯入、來源識別碼、時間及重複資料檢查。 | 尚無機構欄位與 API，未假裝完成院內系統串接。這項需要合作機構提供資料契約後才能實作。 |

## 自動化驗收

指令：`python -B -m unittest -v test_care_console`。

結果：33 項通過，執行時間 74.162 秒。測試使用暫存資料庫、離線替代服務，阻擋外部網路連線；未消耗模型 API 額度，未發送 LINE 訊息。

本輪新增的 13 項檢查涵蓋獨立接班帳號、待辦排序與原因、家屬不可取得內部進度、照服員查看範圍、接手者更新限制、版本衝突、交班欄位與接收者檢查、確認後轉移、過時交班拒絕、更新後重提、結案取消交班及保留紀錄、原始訊息與服務摘要、追蹤原因、重啟保存。原有登入、權限、CSV、轉床、備份等檢查一併通過。

測試過程發現輸入分級事件先於案件建立，兩者時間相差極短，原先時間篩選可能排除該分級紀錄；已改為顯示最近保存的相同風險層級事件，並修正畫面說明，完整測試重新執行通過。

## 網頁操作驗收

1. 家屬登入只看見 R001，沒有工作人員訊息待辦及人工處理頁。
2. 家屬送出明確標示虛構的轉人工需求，護理師首頁出現原因、近期詢問、時間及接手入口。
3. nurse 接手並保存三欄交班內容，指定 nurse2；畫面仍顯示 nurse 為目前接手者。
4. nurse2 登入同一網址，篩選交班給我，閱讀完整內容後確認接收；目前接手者改為 nurse2。
5. nurse2 送出虛構人工回覆，訊息紀錄保存接班帳號名稱；案件仍維持人工處理。
6. 已驗證更新紀錄保留未保存進度，以及重新載入保存內容；未保存的測試文字沒有寫入資料庫。
7. 以 390 × 844 檢視首頁：工作待辦採單欄排列，頁面寬度沒有橫向溢位；完成後恢復正常視窗尺寸。瀏覽器未記錄前端 error／warn。
