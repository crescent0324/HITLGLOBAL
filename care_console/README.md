# 護理之家照護協作台：本機體驗環境

依「各種角色都會使用、看板資料來自院內、先建立環境」的條件建立。這是獨立的模擬環境，原論文程式、測試結果與 LINE 設定未修改。

## 啟動

1. 雙擊本資料夾的 `start.cmd`。
2. 保持命令視窗開啟，瀏覽 `http://127.0.0.1:9465/`。
3. 選擇院內工作人員帳號，輸入體驗密碼 `CareDemo2026!`。家屬與住民沒有網頁登入權限。
4. 登出後可切換其他角色。關閉服務時，在啟動視窗按 Ctrl+C。

已由 Codex 以背景方式啟動時，不必再開第二份。停止背景服務可在本資料夾執行 `powershell -NoProfile -ExecutionPolicy Bypass -File .\stop.ps1`。此腳本先核對 PID 及本專案的 run.py，避免停止原論文程式。

GitHub 版啟動腳本只使用本資料夾的 `.venv`。首次下載後，先依下列指令建立環境並安裝套件，再執行 `start.cmd`。

移到另一台電腦時，可自行使用 Python 3.12 建立 `.venv`，再安裝 `requirements.txt`。不會自動安裝軟體。

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
```

## 院內網頁帳號

| 帳號 | 身分 | 預設查看範圍 | 可操作內容 |
|---|---|---|---|
| admin | 管理者（護理長／IT） | 6 位住民 | 本機暫為合併管理角色：看板、回報、人工處理、轉床、匯入、授權、備份 |
| nurse | 護理師 | 6 位住民 | 看板、回報、人工接手與回覆、結案、轉床、匯入 |
| nurse2 | 接班護理師 | 6 位住民 | 與 nurse 相同；獨立帳號供交班體驗 |
| caregiver | 照服員 | R001、R002 | 查看、詢問、記錄觀察；回報狀態固定為尚未評估 |

家屬與住民的預定使用入口為 LINE。資料庫的 `family`、`resident` 只保留作為模擬 LINE 聯絡身分，目前均配對 R001，無法登入網頁或呼叫操作台 API；以前建立的工作階段也會被拒絕。本版尚未完成真實 LINE 配對或手機收發。

護理長的照護管理與 IT 的系統維運，正式部署前需分開設定權限；目前仍是一個合併管理角色，尚未完成二者的權限隔離。管理頁已分開「院內人員」及「LINE 聯絡人配對」，外部聯絡人不列在網頁人員帳號清單。

以上共用密碼僅供 localhost 體驗。本版拒絕遠端 IP 與外部 Host，不適合直接放上雲端或用 tunnel 公開。

## 建議一次測完整個流程

1. 以護理師登入：看 6 張住民卡片，確認 R005、R006 沒有量測資料。卡片的「需追蹤／需優先確認」來自虛構來源紀錄，沒有用數字推論健康狀況。
2. 護理師開啟 R001 的「服務對話」，展開「流程測試（本機）」，選「LINE 傳入訊息模擬」及已配對的模擬聯絡人，輸入「想了解喘息服務」，再輸入「轉人工」。此功能由工作人員驗證流程，訊息只寫入本機，操作紀錄另外保存操作者。
3. 以護理師登入：首頁「訊息待辦」列出 R001、轉人工原因、近期詢問、等待時間與接手者。點「查看並接手」進入人工處理，接手後可填寫人工回覆及處理進度。
4. 以護理師模擬住民 LINE 身分輸入一般問題：訊息仍依配對住民保存。人工處理中會記錄需求並等待工作人員，直到結案才恢復自動處理。未配對的身分無法模擬向該住民傳入訊息。
5. 以照服員登入：只會看見 R001、R002，可新增觀察紀錄，不能替代護理師設定評估狀態。
6. 護理師可將 R001 從 A101 轉至空床 A107；紀錄、帳號權限與對話都仍屬於 R001。目的床已有住民時會拒絕。
7. 在「院內資料匯入」下載範本，使用虛構數值測試。每次 1–500 筆，必須確認資料為虛構。資料錯誤時整批不寫入；相同來源識別碼和內容會略過，內容衝突時拒絕整批匯入。
8. 管理者可增加或撤銷模擬 LINE 聯絡身分與住民的配對；撤銷後，該身分不能再向這位住民的本機對話傳入測試訊息。此功能尚未接入真實 LINE 或對外資料查詢。

本機看板每 15 秒重新取得資料；頁面顯示最近成功同步時間。這是資料庫更新，不是已完成院內設備即時監測。

## 處理進度與交班

1. 以目前接手帳號填寫「已處理內容、下一步、待確認事項」。前兩欄必填，內容由操作人員填寫。
2. 選擇另一個可接班帳號，按「保存進度並提出交班」。原接手者仍負責，案件持續人工處理。
3. 登出後以指定接班帳號登入同一網址。首頁篩選「交班給我」，開啟案件，閱讀交班內容後按「確認接收交班」。此時才轉移接手權限。
4. 若交班提出後出現新訊息或回覆，接收會被拒絕；原接手者須更新內容並重新提出交班。保存新進度也會取消先前未接收的交班。
5. 新接手者可回覆、更新進度或繼續交班。完成後填寫處理結果並結案，才恢復自動處理。先前案件的結案紀錄保留於人工處理頁。

開啟的住民視窗可按「更新紀錄」取得其他帳號的變更；同案件未保存的進度文字會保留。兩個視窗同時編輯時，舊版本不能覆蓋已保存的新版本，可按「重新載入已保存進度」後再確認。

卡片分別顯示最新量測回報、最近一次已評估紀錄與訊息處理狀態。「照護回報需確認」依最近已評估紀錄列出；新回報若為「尚未評估」，不會解除先前的追蹤提示。已評估紀錄取自可評估角色保存的來源狀態，依觀察時間排序，不依入庫先後推定。各紀錄仍須核對時間，不表示目前健康狀況。新增需追蹤或需優先確認的回報時，必須填寫原因。

住民視窗另外顯示本次讀取時間。關閉或按 Esc 時，有未保存／未送出的表單內容會顯示「繼續編輯／放棄變更」。重新載入已保存進度前也會提醒。這項提醒不代表資料已自動保存；工作階段到期、程式中止等情況仍須重新確認內容。

## 資料與重現

- `runtime/facility.sqlite3`：體驗帳號、住民、床位配置、查看權限、照護觀察、訊息來源、處理進度、交班紀錄、操作紀錄。
- `runtime/core/research.sqlite3`：獨立的對話、風險分級、人工案件與生成工作資料庫。
- `runtime/environment.json`：識別此環境，防止誤用既有資料庫。
- `runtime/session.key`：登入工作階段的本機金鑰；每次啟動讀取已存值。
- `runtime/core/config.local.json`：獨立設定。模型、真實 LINE 均預設關閉，沒有帶入原系統金鑰。

住民身分與床位配置分開保存，轉床不改變住民識別碼。量測保存觀察時間、入庫時間、來源識別碼與填寫者。更正資料新增來源紀錄，不覆蓋原紀錄。CSV 時間必須含時區；未知量測留白。

「備份」下載兩個 SQLite 快照、manifest 與環境識別檔，未含 API 設定及 session.key。還原請使用全新的目錄：facility.sqlite3 放根目錄、core.sqlite3 放在 core/research.sqlite3、environment.json 放根目錄、core-environment.json 放在 core/integration-environment.json；不要直接覆蓋正在執行的資料庫。由測試程式驗證快照可以在新目錄重新載入。

測試指令：

```powershell
.\.venv\Scripts\python.exe -B -m unittest -v test_care_console
```

測試使用暫存資料庫與明確的離線替代服務，阻擋外部網路連線，未消耗 API 額度。

## 已完成與尚未完成

已完成：角色登入與後端權限檢查、住民看板、訊息待辦、處理進度與確認交班、量測來源與時間、照護回報、共享住民對話、固定長照服務摘要、人工接手／回覆／結案、CSV 匯入、轉床、帳號授權、SQLite 備份。

尚未完成：真實 LINE 帳號連結、真實院內資料介接、護理之家正式服務資訊、線上模型回覆驗收、雲端常駐部署及實際護理師體驗。

模型停用時，中風險會進入人工確認，供護理師直接回覆；不會產生模型草稿。草稿審閱沿用原型控制，需先在隔離環境以啟用模型的測試驗證後，才接入此體驗版。

正式場域接入前，需由合作機構確認工作人員帳號建立與停權、各角色可見的資料／對話範圍、住民與家屬 LINE 身分確認、資料授權、院內欄位、同步頻率、責任窗口及服務流程。加入 LINE 好友與院內住民配對是不同步驟；住民資料必須依機構確認的授權範圍提供。現有範圍只是試用設計。

常駐部署要另設 HTTPS 主機、正式登入、機構與住民授權、備份／復原及服務健康檢查；屆時重新設計遠端入口，不公開目前的本機管理介面。
