# 下一輪MVP決策

本文件為D＋S的條件式建議。本輪只完成流程研究與訪談材料；不開始開發、不授予護理長新權力、不接真實LINE、不自動改派。現有R基準及公開來源見 [SOURCES](SOURCES.md)。

## 本輪可以決定與仍不能決定的事

可以決定：固定使用七類職務、四層權限、責任ID與最少範圍的訪談框架；把家屬詢問、正式護理紀錄、申訴與人員異動分開驗證；保留H0唯讀作目前基準。

尚不能決定：哪一位實際主管可提案／核准／改派、誰代理夜班、社工與行政的臨床資料範圍、個別案件回覆時限、跨專業結案標準，以及是否進行正式試點。這些需要機構證據，不能從公開產品模組、評鑑項目或研究者推論直接推出。

## 優先建議的理由與可推翻條件

先以M0與M1比較，可利用現有唯讀監控及人工交班，不先引入例外轉移權。這個建議依G02／G03的問題假設，不是訪談結論。若U09～U12證明原責任人失效是主要風險，且只有M2能解決，先完成核准、接受與帳號生命週期依賴再另開實作任務。

若機構找不到可用的獨立核准或接受者、沒有故障時接續安排，M2維持未核准，改用機構既有人工替代程序並記錄不足。若U16顯示行政／社工不需進系統即可有效處理，M3不為了湊齊角色而開發。

| 假設 | 會推翻建議的證據 | 下一步 |
| --- | --- | --- |
| H0加院內協調可能已足夠。 | 多班別人員反覆無法指出誰接獲缺口，且實際程序沒有追蹤。 | 比較M1，先確認受理窗口。 |
| 需求提案可以先不改owner。 | 失權案例即使已有提案，仍無制度能合法完成接續。 | 排M2前置法遵與業務確認，不讓提案假裝接手。 |
| 最少資訊足以跨專業分流。 | U16指出特定受限欄位確為完成該業務必要，且有合法依據。 | 逐欄重審，不直接開放所有原文。 |
| 程式能減少重工。 | 觀察顯示多一套表單只增加重複登打。 | 優先引用原系統或調整最少紀錄，取得契約前不假定API。 |

## 若選M1，下一個實作任務至少要包含

- 對已授權住民提出／修改自己的需求、撤回、讀取狀態，各自明確能力與資料投影；不變更owner。
- 受理者的身分、可見範圍與人工確認；通知成功與業務受理分開。
- request_id、case_id、版本、理由代碼、提出／受理人及時間；臨床自由文字不送給IT。
- 護理長仍不能代回覆、接手或結案；社工／行政不能借nurse角色登入。
- 越權住民、失權工作階段、新訊息、撤回、多人同時操作、網路結果不明與反覆提交的負向測試。
- 空資料、錯誤、篩選／草稿保護、班別與裝置的實際可用性驗收。

這段是規格輸入，沒有宣告端點已存在，也沒有承諾自動提醒或服務時限。

## 明確延後

自動／無條件主管改派、AI醫療急迫判斷、正式LINE收發、完整排班／人事／帳務／給藥ERP、無契約的第三方資料介接、全院原文匯出及正式臨床成效宣稱均不在本輪。未來是否需要由機構情境與合法依據決定，不能由競品有模組就推定應全部重做。
