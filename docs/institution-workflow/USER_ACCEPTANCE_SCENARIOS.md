# 虛構情境操作與驗收表

狀態：可供主持人準備的訪談腳本。尚未有實際護理師或護理長完成本輪任務；所有受訪、觀察及機構驗收欄位均留空。R任務可用目前本機介面；D情境卡只推演未實作功能。不能把紙本決定記成系統已核准或已改派。

## 1. 主持人準備

使用本分支或基準 main 的獨立副本。只建立新的虛構資料目錄，不指向原 runtime、原論文環境、機構系統或真實住民。受訪者不用安裝工具、操作SQL或提供個人登入資料。

在care_console/使用既有requirements與Python3.12環境；若尚未安裝，依[專案說明](../../care_console/README.md)由主持人準備。在Windows可用：

```powershell
# SESSION-NEW 必須換成這次全新的場次碼；路徑存在就另取新碼，不刪舊資料。
Test-Path -LiteralPath runtime/uat/SESSION-NEW
python -B run.py --port 9468 --data-dir runtime/uat/SESSION-NEW
```

確認Test-Path結果為False、連接埠未由其他程序使用，再啟動。瀏覽 http://127.0.0.1:9468/；只監聽localhost。保持全新示範環境的模型停用、不設定API或LINE金鑰、不建立公開通道。無法確認環境來源時改用紙本卡，不用真實環境替代。

目前體驗帳號為nurse、nurse2、head_nurse、caregiver、admin，公開示範密碼CareDemo2026!；只用於此虛構localhost。切換帳號先保存或明確放棄測試輸入並登出。頭銜卡不改帳號角色。可用兩個獨立瀏覽器設定檔演練接班，或依腳本輪流登入，記錄採用方式。

既有自動展示可讓開發／主持人先檢查基本環境：

```powershell
python -B demo_monitor.py --output runtime/uat/rehearsal-SESSION-NEW.json
```

展示使用自己的暫存虛構資料，與受訪者場次分開；不是現場驗收，也不預先幫受訪者把任務做完。每一場使用新資料夾，前一場的錯誤與紀錄保留，不能清掉再補稱第一次成功。

## 3. 現有介面的連續任務

### U01 建立與接手（護理師，R）

1. nurse登入、開R001，進「服務對話」，選「服務對話與回覆對象」中的家屬聯絡對話。
2. 展開「流程測試（本機）」，測試訊息來源選「LINE 傳入訊息模擬」，模擬聯絡人選家屬體驗身分（ID為family），送出F-M1。這不是向LINE送訊息。
3. 進「人工處理」，先說出誰目前負責，再按「接手此案件」。記下住民、聯絡對象及case_id。
4. 填F-P1並「保存進度」。主持人記錄操作協助與重複輸入，不提供「正確答案」暗示。

預期：接手前是待接手且無責任ID，接手成功後是nurse；未知內容不由系統補成已處理。接手、保存與出現待辦不代表家屬已讀或正式照護已完成。

### U02 提出但尚未接受（護理師＋護理長，R）

1. 延續U01，nurse指定nurse2，按「保存進度並提出交班」，先不接受。
2. 切到head_nurse，找到同一案件與歷程。各自回答「現在誰負責、下一步是什麼、接班者接受了嗎」。
3. 請護理長指出自己目前能做的操作；不要教他使用不存在的改派功能。

預期：責任仍是nurse；交班待接受包含在已接手，不能多算一件。護理長只讀授權摘要與歷程，沒有回覆、接手或改派按鈕。

### U03 交班後有新資訊（兩位護理師，R）

1. nurse在同一對話送F-M2；nurse2嘗試接受原交班。
2. 請nurse2說明錯誤後下一步。主持人不要求用其他人帳號繞過。
3. nurse確認新資訊、更新F-P1並重新提出交班，記錄新的有效狀態。

預期：舊接受被拒，原責任不被偷偷換人；更新內容後才可重提。錯誤及未保存文字要可辨認，不能把舊畫面當成功。

### U04 指定接班者接受（接班護理師，R）

1. 延續U03，nurse2登入，從「交班給我」開同一案件，讀已做／下一步／待確認。
2. 明確接受後，再各自說出目前責任ID。
3. 回到nurse，確認已無代回覆或代結案資格；不為了展示重新授權。

預期：接受成功才轉成nurse2，原責任在歷程保留。若看見被取消或過時版本，先重新讀取，不盲目重按。

### U05 回覆與結案（接班護理師＋護理長，R＋D判斷）

1. 主持人給兩張結果卡：A「虛構聯繫安排已確認，沒有剩餘事項」；B「已回覆但外部事項尚未接受」。先請人員說明哪張可以依現行制度結案。
2. R介面只操作A：nurse2送出「虛構：已確認聯繫安排，本機記錄回覆」，填結果再結案。
3. head_nurse以已結案篩選核對同一案件的責任與歷程。B僅以紙本記錄判斷，不把尚未完成標成完成。

預期：軟體結案、聯繫是否完成與照護事項的完成分開。臨床／正式LINE及家屬手機收件未由此驗證。

### U06～U08 範圍與撤權（護理長、照服員、IT協助，R）

U06：另以nurse在R003建立一件虛構測試，head_nurse重新查詢時不可看到它。要求護理長說出查詢範圍；轉床也不能作為讀其他住民的理由。

U07：nurse查看R001另一位聯絡人的獨立對話，核對F-M1不會被共享；切caregiver，只操作照護回報，服務對話／人工處理／案件監控不可取得。請參與者指出工作上真正缺少的欄位，不臨時打開家屬內容。

U08：只在此場次虛構環境，由主持人用admin的「人員與授權」取消head_nurse對R001的範圍。head_nurse重新查詢及開啟既有歷程，不可恢復R001內容；原查詢中晚到的資料亦不應復活。記錄結果後由主持人恢復場次原設定，保留授權事件。不把這個範圍取消冒稱正式員工停權已完成。

## 4. 未實作的情境卡任務

每張卡印出「角色／可見欄位／目前責任／未完成工作／這次注入變化」。提供空白動作卡：查看、提出需求、核准、接受、拒絕／退回、改用院內聯絡、保持待確認。參與者排列後，每一步記錄誰可做、依據及責任何時改變。主持人只移動紙卡，不修改程式或資料庫來模擬權限成功。

| ID／模式 | 參與角色與前提 | 要做的具體任務 | 應觀察的安全結果與回饋 |
| --- | --- | --- | --- |
| U09 D | 護理師、護理長；F-X1，原人仍有資格但不能登入。 | 比較整案移轉與代理子事項兩種卡，排出核准、接受與回任步驟。 | 沒有借帳號；能指出中間實際照護安排及回任後不自動回收案件。 |
| U10 D | 護理長、行政／IT觀察；F-X2的離職版本。 | 放入生效時間卡，決定業務交接與存取處置各由誰確認。 | 不為完成交班延後必要撤權；保留歷史ID並識別責任缺口。 |
| U11 D | 護理長、IT；F-X2的停權版本。 | 在核准後但接受前放入撤權卡，重新判斷可否接受。 | 舊核准不賦予新資格，不能讓失權者再登入確認。 |
| U12 D | 護理長、負責窗口；無有效owner，無合格候選人。 | 用H0～H3卡各走一次，指出系統應顯示及院內應處理的事項。 | 護理長看到缺口不等於自己接手；無人能接受時保持未受理並啟動替代程序。 |
| U13 D | 原護理師與接班者；交班未接受，未設定時限。 | 決定現在誰負責、下一次聯繫誰、何時依既有規則啟動替代。 | 不以通知、已讀、下班或游標期限自動移轉；沒有自造法定逾期。 |
| U14 D | 護理長及替代窗口；F-X3。 | 填寫替代聯絡角色及失敗後下一步，另一位人員扮演無回應。 | 沒有實際受理就不標接受；法定職務代理與案件代理另分欄。 |
| U15 D | 護理長、獨立窗口；F-Q1。 | 選哪些人可看每個欄位，將受訴人換成護理長、負責人再走流程。 | 受訴人不能自批結案；原文不進一般監控；有可核對的替代／外部途徑。 |
| U16 D | 護理師、社工、行政；F-S1。 | 用遮蔽資訊卡分配三個子事項，說明完成工作必需哪些欄位。 | 社工／行政不扮成nurse，沒有整段臨床原文也能先提出最少需求。 |
| U17 D | 一人兼任負責人與護理長；提案者就是核准者。 | 排H2／H3卡並指出迴避點；再移除獨立核准人。 | 換職稱不完成自提自批；無可用核准路徑則保持待確認。 |
| U18 D | 護理師、護理長；已回覆、家屬未讀且仍有外部待辦。 | 分別判斷訊息、聯繫、照護與申訴能否結束，寫結案必要證據。 | 沒有一鍵把所有事情當完成；轉介待辦需可追蹤接受，門檻交機構確認。 |
| U19 R或D | 主持人控制的新虛構場次；系統／網路故障。 | R可停止該測試服務後讀取；D用故障卡。請人員排電話／紙本承接與復原核對。 | 只停止已確認歸屬的測試程序，不中斷機構服務；結果不明不盲目重送；補記不偽稱當時已完成。 |
| U20 D | 兩個接受者／舊畫面；已核准提案後新訊息或另一人先接受。 | 依次放入三張變動卡，指出每一次接受是否仍有效。 | 僅一人能成功；最終重核資格、範圍、案件及版本，原責任與失敗事件留存。 |

F-E1穿插於U01或U19：要求指出既有現場／緊急處理管道，沒有得到機構程序時記為S13缺口，不由主持人發明醫療處置或急迫分數。真正有人在現場需要協助時立即停止研究任務，交由機構既有程序處理。
