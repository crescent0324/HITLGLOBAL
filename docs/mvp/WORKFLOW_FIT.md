# 與護理之家實務流程的相符性評估

> 版本說明：本文件保留 PR #2 的設計／驗證基準；2026-10-25 新增的護理長監控、IT 隔離、明確範圍與本輪測試，以 [監控工作台文件](../monitor/README.md) 為準。下列未實作狀態及 admin 描述屬當時版本，不能用來推定目前權限。

查閱：2026-10-25（台灣時間）。結論是：本機 MVP 的「有權人員接手、保留來源、交班接受、回覆及結果留存」方向可支援照護連續性，但尚未證明符合任何一家機構的完整 SOP。待辦追蹤也不能代替專業照護、緊急應變或正式護理紀錄。

本輪沒有訪談、聯絡或觀察真實機構。護理之家以護理人員法設立的類型為主；不能把居服打卡、日照核銷或其他長照機構規則直接套成護家的工作要求。

## 相符與不相符的界線

| 實務工作 | 本輪設計／實作的相符處 | 仍需確認或補足 |
| --- | --- | --- |
| 家屬一般服務詢問 | 一位聯絡人一段對話；有責任人、下一步及回覆結果 | 機構實際由護理、社工或行政哪一方分流；非護理身分尚未建角色 |
| 護理師跨班交接 | 有目前責任、保存內容、指定接班及接受，舊交班不覆蓋新訊息 | 當班名單、休假／臨時缺勤代理、夜班負荷及未接收時的升級程序未確認 |
| 照服員發現狀況 | 可記錄來源與觀察，專業評估另由護理師處理 | 急迫觀察應依機構立即通報，不能只寫在看板等人發現；定向通知未實作 |
| 專業評估與照護計畫 | 保留評估來源與時間，不讓一般訊息替代評估 | B1／B2 的完整評估、照護計畫與跨專業執行仍在 ERP 或機構原流程，不由本 MVP 取代 |
| 意外／緊急事件 | 既有規則停止一般生成並等待適當人工流程 | A1.3 要求機構處理能力及紀錄；聊天排隊沒有現場救援與值班保證，須另定即時通報與替代管道 |
| 家屬申訴或重大意見 | 可保留詢問與責任軌跡 | 正式申訴窗口、回覆權責、調查及年度分析不在現有通用案件中；需院方分流 |
| 主管追蹤 | 可看案件責任、進度與結果，不依同名推定人員 | 獨立監控、工作量／逾期分母、主管／IT 分離與提醒未完成 |
| 品質與評鑑 | 可提供某些工作留痕與來源 | B3 臨床品質指標有專業定義；訊息結案率及回覆速度不能當臨床照護成效 |
| 對外回覆 | 本機具回覆與配對撤銷控制 | 機構服務資料、核准文案、可揭露欄位、真實收件與傳輸證據尚未到位 |

上述對基準的對照屬研究者設計判斷，不是政府認證或通過評鑑的結論。MVP 只處理訊息責任；住民臨床問題即使移交他處，也不能僅因軟體訊息已回覆就宣稱照護問題已解決。

## 第一版範圍調整

保留：一般家屬服務詢問、人工接手、處理紀錄、指定交班、回覆與結案。先在完全虛構、本機、無模型的模式確認動線與負向控制。

延後：正式 LINE、臨床摘要生成、第三方臨床資料、完整護理文件、排班、給藥、人資薪資、財務、庫存與核銷。競品已有的成熟 ERP 範圍優先評估合法整合，沒有公開 API 契約就不假定可直接串接。

正式主管監控實作前，需要先知道主管實際要處理的工作與可見範圍。不可把「管理者看得到所有原文」當成預設需求，尤其現版 admin 尚合併 IT 權限。

## 待機構確認的具體輸入

| 問題 | 需要的輸入 | 對開發的影響 |
| --- | --- | --- |
| 誰在何時處理家屬訊息 | 實際分流、值班、代理與非上班時段安排 | 正式角色、責任移轉及預設工作台 |
| 什麼情況不能等候 | 急迫／申訴／醫療資訊分流與替代聯絡程序 | 顯示文案、升級規則、通知失敗處理 |
| 何時算完成 | 詢問回覆、需外部聯繫、需臨床處理各自的結案條件 | 避免未完成事項過早關閉 |
| 可看哪些資料 | 護理、照服、社工、行政、主管、IT 的住民／欄位／對話矩陣 | 正式最小權限與可揭露資料 |
| 回覆／接班時限 | 各類案件、班別與假日條件，未設定如何處理 | due_at、逾期分母及提醒；不得自行捏造法定時限 |
| 資料及實際使用 | 合法資料範圍、保存、資料來源與可操作的測試情境 | 受控試用與維運責任；原論文資料不混用 |

這些輸入未提供，所以「符合特定護理之家 SOP」與「可正式試點」目前待驗證。它們不妨礙本輪安全修正與虛構展示完成，但會影響下一輪開發優先順序，不能在未確認前擴大真實使用。
