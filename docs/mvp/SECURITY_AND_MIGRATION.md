## 後端資料邊界

| 使用者 | 已授權住民照護資料 | 家屬／院內服務對話 | 案件／草稿／進度／交班 | 操作稽核 |
| --- | --- | --- | --- | --- |
| 照服員 | 可讀、可新增觀察；不能設定護理評估 | 不回傳；指定任何對話參數均 403；不能 POST 共用或家屬訊息 | 不回傳、操作 403 | 不回傳，內部讀取方法亦拒絕 |
| 護理師 | 可讀、回報、評估 | 可依目前體驗範圍讀取 | 可讀；寫入須符合案件 ID、責任 ID、對話與版本 | 可讀授權住民紀錄 |
| admin 體驗角色 | 與護理師相同，另有既有管理工具 | 可讀 | 沒有代替別人回覆／結案的豁免 | 可讀；此角色尚未分成 IT 與護理長 |
| 家屬／住民身分 | 無院內網頁／API 工作階段 | 只有護理師可操作的本機模擬入口 | 不能登入或操作院內案件 | 不能讀 |

照服員的住民詳細回應採允許清單，只有 `resident`、`observations`、`role`。看板保留照護卡片、來源與評估紀錄，`work_queue` 為空；卡片不帶案件存在與數量、風險、狀態或責任人。不是傳送完整資料後再隱藏按鈕。

`ConversationDirectory` 的查詢／建立、`StaffWorkflow.view()`、訊息作者與稽核讀取，也檢查護理／管理角色。拒絕請求不建立對話、不改訊息或案件。照服員仍可使用一般服務資料目錄；共用服務訊息測試入口改為護理／管理角色。

畫面同步移除照服員的對話選單、家屬訊息與人工處理頁籤；登出及角色切換清空先前訊息、收件選項與未送出表單。這是附加的畫面保護，授權仍由後端執行。

## 穩定案件責任

`cases.operator_id` 保存 `users.id`，所有權不依 `display_name`、`username` 或用戶端傳來的操作者。顯示名稱只用於呈現，可重複與變更；正式帳號管理必須另外保證帳號 ID 不重用。

- 接手與接受交班同時寫入責任 ID；既有核心 `operator` 欄在新操作中也保存 ID，供既有核心稽核／草稿流程沿用。
- 回覆、草稿核准／退回、進度、交班、取消與結案，均由工作階段取得帳號 ID 進行後端檢查。
- 接班者尚未接受前，原帳號 ID 持續負責。接受時比對原責任 ID、指定接班 ID、住民／對話／案件及訊息版本。
- 待辦 `mine` 與前端可編輯狀態使用 `operator_id`。API 另提供 `operator_name`；原 `operator` 回應保留為顯示標籤相容欄，不參與授權。
- 更名不造成原帳號失去責任，同名同事不會取得責任；管理者亦不能僅因角色較高而代替目前責任人操作。

未改動風險分類、生成適用性、人工案件保持、撤銷、來源有效性及傳輸安全核心；本輪也沒有改動 `care_console/core/` 的檔案。

## 升級前備份

在建立／更動身分欄位前，檢查既有兩個資料庫及遷移標記。尚未升級時，先以 SQLite backup 保存：

```text
runtime/backups/before-stable-case-owner-v1-隨機識別碼/
  facility.sqlite3
  core.sqlite3
  environment.json
  integration-environment.json
  manifest.json
```

沒有複製設定金鑰與 `session.key`。快照失敗會中止啟動，不能繼續升級。備份不是跨程序持續寫入時的一致性保證；升級前停止舊服務，既有 `run.py` 會鎖住使用中的資料目錄，勿另行繞過鎖定啟動第二個版本。

## 遷移規則

在明確交易內新增 `operator_id`、遷移紀錄及標記，同時處理主資料庫與附加的機構資料庫。故障注入測試確認 DDL 與資料可回復；備份獨立保存。

| 舊資料 | 處理 |
| --- | --- |
| 名稱唯一對應一個護理／管理帳號 | 寫入該帳號 ID，保留狀態、訊息、進度與有效交班 |
| 同名多帳號 | 不猜測；未結案的已接手案件回到待接手，清除可操作責任，保留原進度 |
| 找不到帳號或只對應照服員／外部帳號 | 同樣重新等待接手，沒有新增或提升任何帳號權限 |
| 無法確認身分的未結案案件 | 取消舊交班與未完成生成，防止舊核准或接受流程沿用 |
| 已結案但無法辨認原責任人 | 保留結案與原遷移記錄，不捏造新的責任 ID |
| 已完成升級後，新增同名或改名 | 不重新比對歷史名稱；標記防止舊案件因後來帳號出現而取得責任 |

`case_owner_migrations` 保存舊案件編號、原責任文字、原狀態、唯一對應 ID、判定及時間。`meta.stable_case_owner_v1` 標示已完成，不清空資料或重設密碼。舊草稿／核心紀錄中既存的顯示文字是歷史描述，不用作目前授權。

無法確認身分者的後續操作：由有權護理人員查閱保留的內容，重新接手後確認進度並重提需要的交班。重新接手是新的、可稽核的責任取得，沒有自動把舊責任指派給任何同名人員。

## 還原及失敗處理

1. 升級失敗立即停止，不對同一目錄同時啟動其他版本。
2. 核對備份的 manifest 與兩個 SQLite 均可讀，保留失敗現場。
3. 使用新目錄還原 `facility.sqlite3` 與 `core.sqlite3`，後者放到 `core/research.sqlite3`；環境識別檔依原結構放回。
4. 使用對應舊程式及全新本機工作階段啟動；不要將備份直接覆蓋正在使用的資料庫。
5. 在虛構副本重做升級與驗收，再決定實際更新。未還原或匯入任何真實住民資料。

本輪通過：唯一對應、同名、找不到、非護理身分、已結案歷史、草稿取消、備份阻斷、故障回復及重啟不重做。備份還原及既有資料不重灌的回歸亦通過。正式帳號停權、跨程序更新及機構資料契約尚未完成。
