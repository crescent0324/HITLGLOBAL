# 床位查詢的住民範圍修正

基準：main `34eb5d6d1812bfb10c8a0a2707c46769fa30ca8d`。查核日期：2026-10-29，Asia/Taipei。

## 問題與修正

護理師的住民範圍縮限後，`GET /api/beds` 原本仍回傳所有住民ID與床位對應。已在原基準用既有工作階段及全新虛構資料重現；沒有將這個舊問題歸咎於文件或UAT合併。

`CareStore.beds` 現在在SQL中篩選：只提供真正沒有目前配置的空床，或登入者目前具有明確access且仍有效住民的配置。只授權R001時，種子資料回傳A101→R001及空床A107、A108；全部撤權後只回傳A107、A108。不回傳其他住民的占用床位，也不把未授權或停用住民的ID改成null，以免被前端當成空床。

原有 `id`、`ward`、`resident_id` 欄位與護理師角色限制保持不變。轉床仍另外驗證住民範圍與目的床占用，查詢結果不賦予額外轉床權。未新增角色、資料庫結構、遷移或前端程式；不觸碰原HITL核心與論文成果。

## 新增回歸案例

新增於 [test_case_monitor.py](../care_console/test_case_monitor.py)，由原測試命令一併執行：

- nurse、nurse2先登入，縮限成R001後沿用既有工作階段，API與資料層都只回傳允許的配置及真正空床；查詢參數不能冒用別人範圍。
- 全部撤權後不回傳任何住民對應；重新授權R004後只恢復R004配置，未快取舊權限。
- R001仍可轉至A107；原A101回到空床，歷史配置不混成目前住民。未授權R002轉床及轉入已占用A102仍遭拒絕。
- 停用住民的占用床位被排除，沒有假裝為空床。匿名、IT、護理長、照服員及外部聯絡人的原角色限制保持。
